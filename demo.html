🎣 Cross-Site Request Forgery (CSRF) Demo
Attack Scenario: An attacker tricks you into making an unwanted request on a vulnerable site. The browser automatically sends your credentials (cookies) with the request, allowing the attacker to perform actions on your behalf.
Malicious Form (attacker's website):
<form action="https://vulnerable-bank.com/transfer" method="POST" style="display:none;"> <input type="hidden" name="amount" value="5000"> <input type="hidden" name="recipient" value="attacker@evil.com"> <input type="submit" value="Click me"> </form> <script> // Auto-submit when page loads document.forms[0].submit(); </script>
How it works:
1. You're logged into your bank (attacker-bank.com)
2. You click a link to attacker's website
3. Browser loads hidden form targeting your bank
4. Form auto-submits with POST request
5. Browser sends your session cookie automatically
6. Bank processes transfer to attacker without your knowledge
Defense: CSRF Token Validation
// Server generates unique token per session app.get('/transfer', (req, res) => { const csrfToken = generateRandomToken(); req.session.csrfToken = csrfToken; res.render('transfer', { csrfToken }); }); // Client includes token in hidden field <form method="POST" action="/transfer"> <input type="hidden" name="_csrf" value="<%= csrfToken %>"> <input type="text" name="amount"> <button type="submit">Transfer</button> </form> // Server validates token before processing app.post('/transfer', (req, res) => { if (req.body._csrf !== req.session.csrfToken) { return res.status(403).send('CSRF validation failed'); } // Process transfer... });
Why it works: Attacker's website cannot access the CSRF token (same-origin policy). Without the valid token, their forged request fails even if they trick you into clicking.
Defense Mechanisms:
1. Token Validation
Server generates unique tokens per user. Every state-changing request (POST, PUT, DELETE) must include the correct token. Attacker cannot access tokens from other origins.
2. SameSite Cookies
Set-Cookie: sessionid=abc123; SameSite=Strict
Browser won't send cookie with cross-site requests. SameSite=Strict is most secure; SameSite=Lax allows safe navigation.
3. Origin/Referer Header Checks
Verify the request came from your domain:
if (req.headers.origin !== TRUSTED_ORIGIN) { reject(); }
Attacker's requests show their domain in the Origin header.
4. Double-Submit Cookie Pattern
Set a random CSRF token in both cookie and request body. Server verifies they match. Works because attacker cannot read cookies from other domains.
🔐 SQL Injection Demo
Scenario: A login form concatenates user input directly into a SQL query without sanitization. An attacker can inject SQL code to bypass authentication or extract data.
❌ Vulnerable Code
Dangerous Query Construction:
// Vulnerable: Direct string concatenation username = userInput // e.g., "admin' --" query = "SELECT * FROM users WHERE username = '" + username + "'"
Resulting Query:
✓ Safe Code (Parameterized Query)
Prepared Statement:
// Safe: Use parameterized queries query = "SELECT * FROM users WHERE username = ?" parameters = [userInput] // Driver/ORM binds parameters safely
What happens with same input:
Parameter: "' OR '1'='1"

The database treats the entire value as a literal string, not as SQL code. No injection possible.
Safe Binding:
Query: SELECT * FROM users WHERE username = ?
Parameters: [literal string - safely bound]
Why SQL Injection Works:
When input is concatenated into queries, special characters like quotes (') become part of the SQL syntax. An attacker can close strings, add boolean conditions (OR '1'='1'), or execute additional commands (UNION SELECT, DROP TABLE).

How to Prevent It:
1. Parameterized Queries / Prepared Statements: Use placeholders (?) instead of concatenation
2. Input Validation: Validate data type, length, format
3. Escape Special Characters: Use database-specific escaping functions (last resort)
4. Least Privilege: Database user should have minimal required permissions
5. WAF (Web Application Firewall): Detect and block suspicious patterns
🔓 Cross-Site Scripting (XSS) Demo
Scenario: User input is rendered as HTML/JavaScript without sanitization. An attacker injects malicious scripts that execute in the victim's browser, stealing cookies, credentials, or performing actions on their behalf.
⚠️ WARNING: The "Unsafe" mode below will actually execute JavaScript! It's safe in this demo environment, but never do this in production. This is for educational purposes only.
What is XSS?
Cross-Site Scripting happens when an attacker injects arbitrary HTML or JavaScript into a web application that gets executed in other users' browsers. There are three types:
• Stored XSS: Malicious script saved in database, executed for all users
• Reflected XSS: Malicious script in URL parameter, executed when user clicks link
• DOM-based XSS: JavaScript code directly manipulates the DOM with untrusted data

Defense Strategies:
1. Input Sanitization (xss library): Remove dangerous HTML tags and event handlers
2. Output Encoding: Convert special characters to HTML entities (<, >, ", etc.)
3. Content Security Policy (CSP): Restrict script sources and inline scripts
4. Template Escaping: Use framework templating that auto-escapes by default
5. Avoid innerHTML: Use textContent, appendChild(), or safe DOM APIs
6. HTTPOnly Cookies: Prevent JavaScript from accessing session cookies
Safe Pattern (Node.js/Express):
const xss = require('xss');
const sanitizedInput = xss(userInput);
// Safe to render: <%= sanitizedInput %>
